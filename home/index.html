UEFI

Unified Extensible Firmware Interface

Sucessor da BIOS

Retrocompatibilidade

Fornece legacy support para os serviços BIOS

Emula o funcionamento da BIOS (legacy mode / CSM)

Vantagens

  • Inicialização mais rápida (boot mais rápido)
  • Arquitetura transparente ao processador
  • Drivers genéricos
    • Ambiente pré-SO flexível (rede, mouse, etc)
    • Acesso remoto
    • Permite reparo/diagnóstico sem necessariamente usar um SO
  • Modo de segurança (secure boot)
  • Fim da limitação de tamanho de discos (2TB)
    • GPT vs MBR - partições (seção anterior)

Reconhecer o firmware

  • Mouse no Setup → indício de UEFI, mas não é prova: há UEFI com Setup só em modo texto
  • Windows: msinfo32 → “Modo da BIOS: UEFI” ou “Herdado”
  • Linux: existe /sys/firmware/efi quando o boot foi por UEFI

BOOT (BIOS/MBR)

Relembrando…

POST → lê o 1º setor do disco de maior prioridade → executa o código do MBR

O bootloader (GRUB) fica gravado nos primeiros setores do disco

BOOT (UEFI)

POST → firmware lê a ESP (EFI System Partition, FAT32) → executa um arquivo .efi

Não existe “código gravado no setor de boot” — só arquivos normais dentro de uma partição

NVRAM

Non-Volatile Random Access Memory

Chip separado dos discos, na própria placa-mãe

Guarda as entradas de boot (Boot0000, Boot0001, …) e o BootOrder

Cada entrada é um ponteiro: “carregue tal arquivo .efi, de tal partição”

efibootmgr -v

BootOrder: 0000,0001

Boot0000* Ubuntu
    HD(3,GPT,5ba3c495-...)  \EFI\ubuntu\shimx64.efi

Boot0001* Windows Boot Manager
    HD(1,GPT,525a162c-...)  \EFI\Microsoft\Boot\bootmgfw.efi

Cada entrada aponta pelo PARTUUID da partição — não pela posição física do disco

Leitura complementar

Dois upgrades

MBR → GPT (tabela de partição)

BIOS → UEFI (firmware)

Quem dá a partida no disco é o firmware, que precisa entender a tabela para ler o sistema

Onde mora o programa de partida

BIOS + MBR

  • Placa-mãe guarda só a ordem dos dispositivos
  • Código que dá a partida: primeiro setor do disco (MBR)
  • Tabela danificada → falha logo ali

UEFI + GPT

  • Placa-mãe guarda o caminho exato do arquivo .efi e a partição
  • Arquivo na ESP, não em setor bruto
  • Trocar o disco de porta não quebra a inicialização

BIOS/MBR × UEFI/GPT

BIOS/MBR UEFI/GPT
Carregador de boot Setor de boot do disco Arquivo .efi na ESP
Preferência de boot Ordem dos dispositivos (grosseira) Entradas nomeadas na NVRAM
Editar pelo SO Sem padrão efibootmgr (Linux), bcdedit (Windows)

Por que isso importa

BIOS/MBR: um único código de boot por disco — trocar de disco, troca o boot junto

UEFI: entradas independentes na NVRAM, cada uma na sua própria ESP — vários discos, vários sistemas, sem “pisar no pé” um do outro

(base para o dual boot, no fim do deck)

Fat32

File alocation table

Sucessor do Fat12, Fat16

File Allocation Table (Tabela de alocaçào de arquivos)

1996

Suporta partições até 2TB

Tamanho de arquivos máximo: 4GB — campo de 32 bits (2^32 bytes)

Limite do sistema de arquivo, não do espaço livre

Nomes longos: até 255 caracteres (desde o Windows 95)

O antigo “8.3” (8 + 3 de extensão) era do FAT original, do MS-DOS

Experimento

Pendrive de 32 GB, vazio, em FAT32

ISO do Windows 10: 4,8 GB

Cabe ou não cabe?

→ “muito grande para o formato do volume”

O armário com prateleiras

Comparativo FAT

Atributo Fat 12 Fat 16 Fat 32
Máx. de clusters ≈ 4 mil (2^12) ≈ 65 mil (2^16) ≈ 268 milhões (2^28)
Tamanho do cluster 512B até 4KB 2KB até 32KB 512B até 32KB
Tamanho máximo do volume 16 a 32 MB 2 GB 2 TB

Valores típicos

Endereço do cluster é o número do cluster no disco (simples)

Comparação com o FAT16

melhorias

Tamanho do cluster mais flexível

Mais confiável

Tamanho de arquivos, partições, extensões

comprometimento

Tende a ser mais lento do que o FAT16

NTFS

New technology file system

Desenvolvido pela Microsoft - Windows NT

Segurança - Ponto de vista de prevenção de danos (blackout) -> Journaling -> log de mudanças - Ponto de vista de acesso aos dados: Permissões e encriptação dos dados

Tamanho dos arquivos

Clusters - Tamanho padrão: 4KB - Clusters menores do que o FAT32 -> Reduz o espaço desperdiçado

Fora do Windows: macOS só lê; Linux lê e grava (driver ntfs3, kernel 5.15+)

Comparativo NTFS vs FAT32

NTFS » FAT32

Arquivos maiores do que 4GB são possíveis (tamanho do arquivo limitado ao tamanho do volume)

Nome de volumes até 32 caracteres

Suporte a compactação, criptografia, indexação

Suporte a clusters de 512 bytes

Muito mais seguro do que FAT32 - Mais fácil de recuperar de erros - Política de segurança e gerenciamento dos dados

Menos vulneráveis a fragmentos

Comparativo NTFS vs FAT32 — onde o FAT32 leva vantagem

FAT32 » NTFS

Mais fácil de danificar arquivos em mídias removíveis - Sistema de arquivo mais complexo - Difícil remoção rápida

Fora do Windows: suporte parcial (macOS só lê)

NTFS tende a ser mais lento - Diretivas de segurança - Complexidade

exFat

Extended file allocation table

(2006)

Menos sofisticado do que NTFS

Rápido

Otimizado para dispositivos removíveis (flash-drives, cartões de memória)

Limite alto do tamanho de arquivos

Suporte em diversas plataformas

EXT3

Distribuições Linux

Evolução do ext, EXT2 (1993)

Ano de lançamento: 2001

Implementação do journaling - Registro (log) das transações - Provê recuperação mais fácil do sistema em caso de desligamento não programado

EXT4

(2008)

Sistema de arquivo padrão para distribuições linux de desktop e servidores atuais

Arquivos de até 16TB

Volumes de 1EB

Não possui suporte padrão no MAC, Windows

HFS,HFS+,APFS

Hierarchical file system for macOS (2Gb,2TB)

1998 -> HSF+ (+journaling, 8EB)

2017 -> Apple file System APFS Otimizado para SSDs

Não tem suporte fora das plataforrmas da apple

ZFS

Zed file system

Integra gerenciador de volumes ao sistema de arquivos -> Foco na proteção dos dados

Multi boot, se forem mais de dois

Dois cenários bem diferentes

Mesmo disco — cenário clássico (Windows + Linux, GRUB): a ordem de instalação importa, Windows sempre primeiro

Discos separados — cada SO no seu próprio NVMe/SSD: cada disco tem sua própria ESP e sua própria entrada na NVRAM

Um SO lê o sistema de arquivo do outro?

Windows não lê ext4 de fábrica → software de interface (Linux Reader, wsl --mount)

Linux lê e grava NTFS (ntfs3)

Ler/escrever ≠ rodar sobre: cada SO continua na sua partição

Estudo de caso: 2 NVMe, Windows + Ubuntu

Disco Conteúdo
nvme0n1 Windows completo: ESP, MSR, C:, recuperação
nvme1n1 Ubuntu completo: swap, root (ext4), ESP própria

Nenhum arquivo de boot de um sistema está gravado no disco do outro

efibootmgr -v

BootOrder: 0000,0001

Boot0000* Ubuntu                -> nvme1n1p3 (ESP do Ubuntu)
Boot0001* Windows Boot Manager  -> nvme0n1p1 (ESP do Windows)

Duas entradas independentes, cada uma no seu disco — nada em comum

Por que isso é seguro (e reversível)

Trocar o nvme1n1 (disco do Ubuntu) por outro não toca em nada do Windows

Recolocar o disco original restaura o Ubuntu, sem reinstalar nada

Isolamento total — consequência direta de como o UEFI trata boot (bloco UEFI)

Pegadinha: entrada pode sumir da NVRAM

Algumas firmwares “limpam” entradas órfãs (apontando pra um disco desconectado) durante o POST

Workaround — recriar manualmente, com o disco já reconectado:

sudo efibootmgr --create \
  --disk /dev/nvme1n1 --part 3 \
  --label "Ubuntu" \
  --loader '\EFI\ubuntu\shimx64.efi'

Só recria o ponteiro na NVRAM — nenhum arquivo no disco é alterado
